## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an unfinished task).
- **[Story]**: the user story in [spec.md](spec.md) the task belongs to.
- IDs in brackets after a task name the requirement (FR-0nn in the spec, FR-nn and NFR-nn on [pages 2](../../docs/solution-design/02-functional-requirements.md) and [3](../../docs/solution-design/03-non-functional-requirements.md)), the acceptance scenario (AC-nn.n), the decision (DEC-nn), the spec's decided-in-the-run item (item n) and the plan's (Pnn) it serves.

## Conventions for every spec task

- Each spec file starts with `# frozen_string_literal: true`, requires the class under test with `require 'application/<file>'` or `require 'infrastructure/<file>'`, and has one top-level `RSpec.describe <Class>` (plan [P1](plan.md#p1), [P19](plan.md#p19); `001` plan [D13](../001-domain/plan.md#d13), [D16](../001-domain/plan.md#d16)).
- One expectation per example; examples of at most 5 lines; at most 3 levels of nesting (`001` plan [D17](../001-domain/plan.md#d17)). A scenario's standard output, standard error, exit status and output file are separate examples sharing one memoised `subject(:run)`.
- Strings that a test compares are copied character for character from the spec: the acceptance scenarios, the [run-stopping messages table](spec.md#run-stopping-messages), and `001`'s domain messages ([SC-003](spec.md#sc-003)). Never change an expected string to match the code.
- The spec's `balances.csv` is the three lines `1111234522226789,100.00`, `1212343433335665,50.00`, `0000123412341234,0.00`, total 150.00. The fixed run time is `Time.new(2026, 11, 7, 14, 30, 5)`; the default output path for it is `output/final_balances_2026-11-07_143005.csv`.
- **Runner scenarios** ([spec item 1](spec.md#item-1), plan [P18](plan.md#p18)): in [`spec/infrastructure/runner_spec.rb`](../../spec/infrastructure/runner_spec.rb), grouped by FR in `describe` blocks, each scenario is a `describe` named after its criterion (for example `describe 'AC-01.4 an invalid file reports every problem and stops the run'`; `RSpec/ContextWording` applies only to `context`, so no `context` text starts with `AC-`; nesting stays within 3 levels: a scenario run for several rows or values gets one `describe` per row or value directly under its FR group, named with the AC ID and the value, for example `describe 'AC-09.5 LOG_LEVEL=INFO'`, never a group inside the AC group, so `RSpec/NestedGroups` holds), with `subject(:run) { run_scenario(files: { ... }, arguments: [...], env: { ... }) }`. `run_scenario` writes the files into a temporary folder used as the current folder; its default files are `balances.csv` as above and `transfers.csv` holding the one row `1111234522226789,1212343433335665,10.00` ([AC-01.1](spec.md#ac-01-1)'s file; [spec item 23](spec.md#item-23)), its default arguments `balances.csv transfers.csv output/final_balances_2026-11-07_143005.csv`, its default environment `{}`. The shared examples `'a completed run'` (`stdout:`, `stderr:` with the default `''`, `output_file: nil`) and `'a stopped run'` (`stderr:`) check each stream exactly, with `<timestamp>`, `<pid>` and `<reason from the system>` matched by `stream_pattern` ([spec item 10](spec.md#item-10)); `'a stopped run'` also checks that standard output is empty, the exit status is 1 and no output file was left ([SC-004](spec.md#sc-004)).
- Where a scenario's standard output is Template A or R, the example builds it with `template_a` or `template_r` from [`spec/support/report_templates.rb`](../../spec/support/report_templates.rb); lines marked **(derived)** in the spec are checked the same way.
- An example that proves an edge case names its DEC ID in its description, for example `stops with UnreadableFile, not NoTransfers, when line 1 cannot be read (DEC-04, DEC-20)`.

## Implementation strategy

### MVP

The MVP is the end of [Phase 3](#phase-3): [`bin/run`](../../bin/run) on the challenge's sample files gives the exact report, the exact final balances (4820.50, 9974.40, 1550.00, 1725.60, 48679.50; total 66750.00 before and after) and exit status 0, through every layer.

### Incremental delivery

1. [Phases 1](#phase-1) and [2](#phase-2): the sample copies, and both files read with every file-level rule.
2. [Phase 3](#phase-3): the sample run works end to end ([US1](spec.md#us1)).
3. [Phase 4](#phase-4): a bad balances file is reported in full and stops the run ([US2](spec.md#us2)).
4. [Phase 5](#phase-5): bad transfers are rejected with one reason each; empty or broken transfers files stop the run ([US3](spec.md#us3)).
5. [Phase 6](#phase-6): the total check and the writer's failure rules ([US4](spec.md#us4)).
6. [Phase 7](#phase-7): arguments, start checks, `LOG_LEVEL` and every exit status ([US5](spec.md#us5)).
7. [Phase 8](#phase-8): every domain scenario through the runner ([US6](spec.md#us6)).
8. [Phases 9](#phase-9) to [11](#phase-11): the design review, the suite checks and the final checks; `003` can start.
9. [Phase 12](#phase-12): the opening balances in the report ([DEC-26](../../docs/design-analysis/design-decisions.md#dec-26)).
10. [Phase 13](#phase-13): `ProcessDailyTransfer` refactored after the code review; the log text comes from `LogMessages`, the parts come as one `ProcessDailyTransfer::Parts`, and nothing a user sees changes.
11. [Phase 14](#phase-14): the application and infrastructure refactored after the code review; `TransferResult` is an application `Data` record, and nothing a user sees changes.
12. [Phase 15](#phase-15): the application and infrastructure code that is not obvious from reading it is commented, and nothing a user sees changes.
13. [Phase 16](#phase-16): each rule is tested once, at the layer that owns it; the runner keeps only what a run through it shows, and nothing a user sees changes.
14. [Phase 17](#phase-17): the application layer requires nothing from the infrastructure layer, and nothing a user sees changes.
