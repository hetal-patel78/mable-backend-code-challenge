### Conventions used in the scenarios

These are copied from [page 2](../../docs/solution-design/02-functional-requirements.md#how-to-read-the-acceptance-criteria), with one addition for runs made by hand:

- **Standard output** (stdout) carries the report only. **Standard error** (stderr) carries error messages and log lines. "(nothing)" means the stream stays empty.
- The **exit status** is 0 for a completed run and 1 for a stopped run ([DEC-25](../../docs/design-analysis/design-decisions.md#dec-25)). In Docker, the exit status of `docker run` is the program's exit status.
- [Page 2](../../docs/solution-design/02-functional-requirements.md)'s runs start at 2026-11-07 14:30:05 local time, from the project root, with the default log level (warn). The runs in this spec are made by hand, or by CI, at a real time: `<run time>` stands for that run's local date and time in the form `YYYY-MM-DD_HHMMSS`, and is the only part of any stream or file name that differs from [page 2](../../docs/solution-design/02-functional-requirements.md) (decided in the run, [item 1](#item-1)), except that on Windows the console streams use CRLF line endings, so they are compared line by line with CRLF changed to LF, while the output CSV is compared byte for byte (decided in the run, [item 15](#item-15)).
- Log lines use Ruby's standard log format. `<timestamp>` stands for the date and time to the microsecond and `<pid>` for the process number, which change on every run.
- The **pushed branch** is `main`, the repository's default branch and the one the submission link opens, after the merged implementation is pushed to it ([DEC-38](../../docs/design-analysis/design-decisions.md#dec-38); [brief Part 2](../../docs/spec-kit/spec-kit-brief.md#part-2-implementation) step 4). Every submission check, every clean checkout and the README's coverage figure are taken on its latest commit ([Clarifications](#clarifications)).
- A **clean checkout** is a fresh `git clone` of the pushed branch into a new, empty folder outside the working repository, with no `output/`, `coverage/` or installed gems carried over (decided in the run, [item 2](#item-2)).
- `<image>` is the Docker image name the README uses, `mable-transfers` (decided in the run, [item 5](#item-5)).

## Clarifications

### Session 2026-11-07

- <a id="clarification-1"></a>Q: Which branch do the submission checks, the clean checkout and the README's coverage figure apply to? → A: `main`, the repository's default branch, the one the submission link opens, after the merged implementation is pushed to it ([DEC-38](../../docs/design-analysis/design-decisions.md#dec-38); [brief Part 2](../../docs/spec-kit/spec-kit-brief.md#part-2-implementation) step 4).
- <a id="clarification-2"></a>Q: How is [`bin/run`](../../bin/run) kept with LF line endings in a Windows checkout, so a Docker image built there still starts it (Git on Windows normally checks text files out with CRLF, and a CRLF first line makes `#!/usr/bin/env ruby` fail)? → A: it is not forced, and nothing needs to force it. The repository has no `.gitattributes` file, and [`bin/run`](../../bin/run) is stored with LF and mode `100755` like every other text file. In a Windows checkout made with `core.autocrlf=true`, Git gives every text file CRLF, [`bin/run`](../../bin/run) included, and RuboCop's line-ending check, `Layout/EndOfLine`, is turned off, so `bundle exec rubocop` reports no offence there, nor in a download with LF files ([DEC-36](../../docs/design-analysis/design-decisions.md#dec-36)). A CRLF first line cannot stop a Docker image built from such a checkout, because the image's default command runs the file through Ruby (`ruby bin/run`, next question); Ruby runs such a file but writes `bin/run:1: warning: shebang line ending with \r may cause problems` on standard error, so the Dockerfile strips the carriage returns from [`bin/run`](../../bin/run) inside the image before it installs the gems (decided in the run, [item 18](#item-18); [DEC-22](../../docs/design-analysis/design-decisions.md#dec-22), [DEC-36](../../docs/design-analysis/design-decisions.md#dec-36), [NFR-04](../../docs/solution-design/03-non-functional-requirements.md#nfr-04)). Research note: with its default style `native`, `Layout/EndOfLine` wants CRLF on Windows and LF elsewhere, which is why [DEC-36](../../docs/design-analysis/design-decisions.md#dec-36) turns it off ([R-3](research.md#r-3) in research.md).
- <a id="clarification-3"></a>Q: What does the Docker image run by default: [`bin/run`](../../bin/run) directly, or through `bundle exec`? → A: `ruby bin/run` directly, as the Dockerfile's default command in exec form (`CMD ["ruby", "bin/run"]`), not through `bundle exec`, so a container started with no command runs the sample files, the exit status of `docker run` is the program's, a CRLF first line in a Windows checkout cannot stop it starting, and any command given after the image name (such as `bundle exec rspec` or `ruby bin/run -h`) replaces it ([DEC-22](../../docs/design-analysis/design-decisions.md#dec-22), [DEC-36](../../docs/design-analysis/design-decisions.md#dec-36), [DEC-37](../../docs/design-analysis/design-decisions.md#dec-37)).
- <a id="clarification-4"></a>Q: Which user does the container run as, given that on a Linux host the mounted `output` file then belongs to that user? → A: the official image's default user (root); the README's run command adds no `--user` option, and the README says in one line that on a Linux host the output file may belong to root ([DEC-36](../../docs/design-analysis/design-decisions.md#dec-36), [DEC-37](../../docs/design-analysis/design-decisions.md#dec-37); `--user` with an arbitrary user id can make Bundler warn on standard error).
- <a id="clarification-5"></a>Q: In what order does the README give its sections after build, test and run? → A: in [DEC-37](../../docs/design-analysis/design-decisions.md#dec-37)'s order: build, test and run (the normal way, Windows, then Docker); the input files; `LOG_LEVEL` and exit statuses; the assumptions; the design reasoning; the test coverage; persistent storage, production items and known limitations; "How this was built"; then the repository layout and the link to the challenge ([DEC-37](../../docs/design-analysis/design-decisions.md#dec-37)). The README also opens with the prerequisites, before build, test and run, and has a troubleshooting section after `LOG_LEVEL` and exit statuses, as [DEC-37](../../docs/design-analysis/design-decisions.md#dec-37) asks for both.

### User Story 1 - A reviewer with Ruby 3.4 runs the sample files with one command (Priority: P1)

A reviewer who has Ruby 3.4 clones the repository, installs the gems with `bundle install`, and runs [`bin/run`](../../bin/run) with no arguments. They get the exact sample result, with no other setup, and the same from any folder ([NFR-04](../../docs/solution-design/03-non-functional-requirements.md#nfr-04); [DEC-01](../../docs/design-analysis/design-decisions.md#dec-01), [DEC-22](../../docs/design-analysis/design-decisions.md#dec-22), [DEC-35](../../docs/design-analysis/design-decisions.md#dec-35)).

**Why this priority**: the rubric's "runs and provides feedback" and "calculates the test files accurately" depend on the program running at once on the reviewer's machine; this is the main way to run ([DEC-36](../../docs/design-analysis/design-decisions.md#dec-36): Docker is the fallback).

**Independent Test**: on a clean checkout on Linux or macOS with the Ruby version in [`.ruby-version`](../../.ruby-version): `bundle install`, then [`bin/run`](../../bin/run), comparing the streams, the exit status and the output file with the sample report and the sample output file.

**Acceptance Scenarios**:

1. **The gems install at the locked versions** ([NFR-04](../../docs/solution-design/03-non-functional-requirements.md#nfr-04); [DEC-01](../../docs/design-analysis/design-decisions.md#dec-01)).
   - **Given** a clean checkout and Ruby at the exact version in [`.ruby-version`](../../.ruby-version), **When** `bundle install` runs, **Then**:
     - Standard output: Bundler's summary line (`Bundle complete!`); not compared exactly.
     - Standard error: not compared.
     - Exit status: 0
     - And [`Gemfile.lock`](../../Gemfile.lock) is unchanged (`git status` shows no change), and only the gems the lock file lists are installed.
2. **The sample files with no arguments** ([NFR-04](../../docs/solution-design/03-non-functional-requirements.md#nfr-04), [AC-08.1](../../docs/solution-design/02-functional-requirements.md#ac-08-1); [DEC-22](../../docs/design-analysis/design-decisions.md#dec-22), [DEC-35](../../docs/design-analysis/design-decisions.md#dec-35)).
   - **Given** that clean checkout after `bundle install`, **When** [`bin/run`](../../bin/run) runs from the project root, **Then**:
     - Standard output: the sample report.
     - Standard error: (nothing)
     - Exit status: 0
     - And `output/final_balances_<run time>.csv` is the sample output file.
3. **From another folder** ([NFR-04](../../docs/solution-design/03-non-functional-requirements.md#nfr-04), [AC-08.4](../../docs/solution-design/02-functional-requirements.md#ac-08-4); [DEC-22](../../docs/design-analysis/design-decisions.md#dec-22), [DEC-26](../../docs/design-analysis/design-decisions.md#dec-26)).
   - **Given** the same checkout, **When** `../bin/run` runs with no arguments from the project's [`docs`](../../docs) folder, **Then** standard output is the sample report with its last line `Output file: <project root>/output/final_balances_<run time>.csv`, where `<project root>` is the checkout's full path as Ruby gives it (the file is outside [`docs`](../../docs), so it is shown in full), standard error is (nothing), the exit status is 0, and the file is written in the project's `output/` folder.
4. **The tests and the style checker on the reviewer's machine** ([NFR-04](../../docs/solution-design/03-non-functional-requirements.md#nfr-04); [DEC-34](../../docs/design-analysis/design-decisions.md#dec-34), [DEC-36](../../docs/design-analysis/design-decisions.md#dec-36)).
   - **Given** the same checkout, **When** `bundle exec rspec` and then `bundle exec rubocop` run, **Then**, for `bundle exec rspec`:
     - Standard output: RSpec's summary with `0 failures`, a `Randomized with seed` line (random order) and SimpleCov's `Line coverage:` line.
     - Standard error: not compared.
     - Exit status: 0
     - And SimpleCov writes `coverage/`.
   - And, for `bundle exec rubocop`:
     - Standard output: RuboCop's summary line, `no offenses detected`.
     - Standard error: not compared.
     - Exit status: 0

### User Story 4 - Every push runs the tests and the style checker on GitHub (Priority: P1)

Every push to the GitHub repository starts a GitHub Actions run that installs the locked gems on the Ruby version in [`.ruby-version`](../../.ruby-version), runs RSpec and RuboCop, and fails if either fails. ### Edge Cases

- **Docker with no `TZ`** ([DEC-37](../../docs/design-analysis/design-decisions.md#dec-37); [page 9](../../docs/solution-design/09-considerations.md) risks): the container uses UTC, so the file name carries the UTC time; the run is otherwise the same. The README says to set `TZ`.
- **Docker with no `output` mount** ([DEC-37](../../docs/design-analysis/design-decisions.md#dec-37)): the file is written inside the container and is lost when the container is removed; standard output still shows the report. The README gives the mount in its run command.
- **Docker with a mount and an existing file of the same name** ([DEC-25](../../docs/design-analysis/design-decisions.md#dec-25), [DEC-27](../../docs/design-analysis/design-decisions.md#dec-27)): the run stops at the start checks, as [AC-09.3](../../docs/solution-design/02-functional-requirements.md#ac-09-3) states, and the reviewer's file is unchanged.
- **Docker with typed paths** ([DEC-22](../../docs/design-analysis/design-decisions.md#dec-22)): files outside the image must be mounted; the README's commands use only the sample files, and a reviewer passing their own files mounts them the same way as `output`. The README says so in one line (decided in the run, [item 6](#item-6)).
- **A lock file made on Windows** ([DEC-01](../../docs/design-analysis/design-decisions.md#dec-01)): [`Gemfile.lock`](../../Gemfile.lock) must also list the Linux platforms CI and Docker use, or a frozen install there fails (decided in the run, [item 4](#item-4)).
- **[`bin/run`](../../bin/run) on Linux and macOS** ([DEC-22](../../docs/design-analysis/design-decisions.md#dec-22)): it must start as [`bin/run`](../../bin/run), so it is committed as executable, starts with `#!/usr/bin/env ruby` (added here if `002` left it out, decided in the run, [item 16](#item-16)) and is stored with LF line endings in Git (decided in the run, [item 7](#item-7)). On Windows and in a Docker container it is run as `ruby bin/run`.
- **Line endings in a Windows checkout** ([DEC-04](../../docs/design-analysis/design-decisions.md#dec-04)): Git may give text files CRLF line endings on Windows; the CSV library reads them the same, and the output file is LF on every system ([page 10 pick 17](../../docs/solution-design/10-traceability-glossary-assumptions.md#pick-17)). [`bin/run`](../../bin/run) is not treated differently: it too gets CRLF in a Windows checkout made with `core.autocrlf=true`, and RuboCop's `Layout/EndOfLine` is turned off ([DEC-36](../../docs/design-analysis/design-decisions.md#dec-36)), so `bundle exec rubocop` reports no offence there ([FR-018](#fr-018); decided in the run, [item 17](#item-17)). A kernel cannot start a CRLF `#!/usr/bin/env ruby` line ("No such file or directory"), so nothing here starts [`bin/run`](../../bin/run) through its shebang on Windows or in Docker: Windows runs `ruby bin/run`, and the Docker image runs `ruby bin/run`. Ruby on Linux warns about a CRLF `#!` line on standard error (`bin/run:1: warning: shebang line ending with \r may cause problems`), so the Dockerfile's `RUN` instruction strips the carriage returns from [`bin/run`](../../bin/run) in the image, and an image built from a Windows checkout writes nothing more on standard error than one built from a LF checkout (decided in the run, [item 18](#item-18)). There is no `.gitattributes` file.
- **Docker on a Linux host** ([DEC-36](../../docs/design-analysis/design-decisions.md#dec-36), [DEC-37](../../docs/design-analysis/design-decisions.md#dec-37)): the container runs as the image's default user, root, so the file it writes in the mounted `output/` folder may belong to root; the README says so in one line, and the run command adds no `--user` option ([Clarifications](#clarifications)).
- **A Windows reviewer with Docker Desktop** ([DEC-37](../../docs/design-analysis/design-decisions.md#dec-37)): the mount path differs between shells, so the README gives the Docker run command for a POSIX shell and for PowerShell (decided in the run, [item 5](#item-5)).
- **A run from another folder on Windows** ([DEC-22](../../docs/design-analysis/design-decisions.md#dec-22), [DEC-26](../../docs/design-analysis/design-decisions.md#dec-26)): `ruby ..\bin\run` from [`docs`](../../docs) shows `Output file: <project root>/output/final_balances_<run time>.csv`, the checkout's full path as Ruby gives it (with forward slashes, for example `C:/...`), as in [AC-08.4](../../docs/solution-design/02-functional-requirements.md#ac-08-4).
- **No Ruby 3.4 on the Windows machine used for the check, or no Docker** ([brief Part 2](../../docs/spec-kit/spec-kit-brief.md#part-2-implementation) step 3): the hand check that cannot be run is listed in the run report as left for the developer, never marked as passed.
- **A newer Ruby 3.4.x released after [`.ruby-version`](../../.ruby-version) is set** ([DEC-01](../../docs/design-analysis/design-decisions.md#dec-01)): [`.ruby-version`](../../.ruby-version) and the Dockerfile keep the same version; the version is changed in both at once, never in one.
